**Summary:** The Steam identity invariant now holds, and the prior S1, S4, S5, S6, S7 fixes are in place. I found no authentication or ownership bypass. The remaining defects are availability-class: the shipped rate-limit configuration turns per-client caps into site-wide caps, and two fail-closed capacity limits can be filled cheaply by one client. No missing database symbols.

## Verified (not repeated)

- `src/lib/steam-auth.mjs:98-106` builds one frozen record, fails closed on any repeated `state` or `openid.*` key. `callback/route.ts:49-74` validates, verifies, and issues the session from that same record. The nonce is replay-checked after provider success (`route.ts:70-71`, atomic insert at `account-store-postgres.ts:150-160`). `tests/security-auth.test.mjs:86-180` covers duplicates, signed-field list, nonce staleness, ambiguous provider replies, and nonce reuse.
- Guest IDs cannot claim `account:` (`guest-identity.mjs:2`). All party mutations are POST with origin and JSON checks. Deletion runs under a row lock in one transaction (`account-store.ts:297-316`, nested via `database-client.ts:27-36`) and FK cascades cover sessions, rounds, and alpha sessions. All `queue_arcade_*` tables referenced in `src/lib` exist in `database-schema.mjs`.

## Findings

**F1. High. Shipped deployment makes every rate limit global.** `render.yaml:40-41` sets `ARCADE_TRUST_PROXY=none`. `rate-limit.mjs:35-42` then returns `"unknown"` for every request, so every address bucket is shared by all users. Demonstrated effects in production: 20 requests per minute to `/api/auth/steam` (`steam/route.ts:11`, constant identity `"steam"`) block sign-in for everyone; 20 to the callback (`callback/route.ts:43`) block all completions; 300 POSTs to `/api/votes` (`votes/route.ts:31`) block all voting; 10 to `/api/me` DELETE and 120 GETs (`me/route.ts:13,40`) block profile loads and deletions. No credentials needed, and `Origin` is attacker-settable outside a browser. Render always fronts the container with its proxy, so `none` is the wrong setting there. Fix: set `x-forwarded-for` for Render, and have `production-config.mjs:38` fail or warn when `none` is combined with a proxy-only platform marker such as `RENDER`. Regression: a production-config test asserting `none` is rejected when `RENDER` is set, and a route test that two different forwarded clients do not share the steam-auth bucket.

**F2. High. One client can exhaust the limiter and lock out all new visitors.** `rate-limit.mjs:9,70-78` fails closed for any new key once 20,000 buckets exist. Identity buckets are created before any ownership or room check: `/api/rounds` allows 9,000 rotated `playerId` values per address per minute (`rounds/route.ts:61`), `/api/private-rooms` GET another 9,000 (`private-rooms/route.ts:41`, before the member check at line 46), and the `touch` POST another 9,000 (`route.ts:80-87`, before the room lookup at line 90). That is 27,000 new buckets per minute from one address, above the cap, so every other client's first request on any route returns 429 until the attacker stops. Works with or without a trusted proxy. Fix: cap distinct identities per address per window, or evict the attacker's scope rather than reject globally. Regression: rotate IDs on two scopes from one address until the cap, then assert a new address on `steam-auth-start` is still allowed.

**F3. Medium. Party capacity is a cheap global lock.** `private-rooms.mjs:23,382` caps rooms at 500 total, and rooms persist 30 minutes idle (line 8). `private-rooms/route.ts:79` allows 8 creates per identity, but rotated guest IDs reach the 300 address cap, so ~500 requests block party creation for everyone for 30 minutes, repeatable. `tests/private-rooms.test.mjs:467-484` only confirms the fail-closed cap. Fix: cap rooms per host identity and per address, and evict the oldest empty waiting room of the same host. Regression: one host or one address cannot hold more than N rooms.

**F4. Low. Private-room media served without membership.** `round-audio/route.ts:51-60` and `round-image/route.ts:14-23` resolve a private round from the code embedded in the round ID and never call `privateRoomMember`. Anyone with a code can pull the party's clue audio and consume encoder and cache slots. Fix: require membership via `playerId` or session for private round IDs.

**F5. Low. Round pruning inside the vote transaction.** `vote-store-postgres.ts:297,111-124` runs `maybePruneRounds` on the transaction opened by `recordRoundOutcome` (`vote-store.ts:659-662`). A caught error there, such as a 5s `lock_timeout` against the minute cleanup job, leaves the transaction aborted so the vote fails with 503. Move the prune outside the transaction or onto the pool.

## Test gaps worth closing

- No test that a mismatched state cookie, a wrong-origin `return_to`, or a different `state` in `return_to` is rejected (`steamAssertionIdentity` line 117 is only exercised with the matching value).
- No test for F1 or F2 scenarios; `tests/security-protection.test.mjs:151-170` asserts the fail-closed capacity behaviour as desired, which is the F2 hazard.
